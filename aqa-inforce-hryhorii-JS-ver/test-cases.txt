Field rules used in the test data (from the booking / room services)
  Firstname : required, 3-18 characters
  Lastname  : required, 3-30 characters
  Email     : required, well-formed e-mail address
  Phone     : required, 11-21 characters
  Dates     : check-in must be before check-out; already booked dates cannot be booked again
  Room type : Single | Double | Twin | Family | Suite;  price 1-999

Common test data
  VALID   : Firstname=John, Lastname=Tester, Email=john.tester@example.com, Phone=01234567890
  ROOM    : at least one room exists (automation creates its own room through the Admin API)

Common preconditions (all UI cases)
  P1. Browser is open, the User App is reachable.
  P2. A room exists. Its reservation page is opened from the home page with the button
      "Book now" (URL: /reservation/{roomid}?checkin=YYYY-MM-DD&checkout=YYYY-MM-DD).
      The calendar shows the selected days as a "Selected" bar.

---------------------------------------------------------------------
TC-UI-01  Room can be booked with valid data                [Positive]
Priority: High     Automated: user-spec.cy.js
---------------------------------------------------------------------
Steps:
  1. Open the reservation page of the room (P2) with dates in the future, e.g. 3 nights.
  2. Click "Reserve Now" under the calendar. -> "Book This Room" form is shown.
  3. Enter VALID data: Firstname, Lastname, Email, Phone.
  4. Click "Reserve Now" in the form.
Expected:
  - POST /api/booking is sent with the entered data and the selected dates, response 201.
  - Card "Booking Confirmed" is shown with text "<checkin> - <checkout>".
  - Admin API shows exactly one booking for this room with the same name and dates.

=====================================================================
API TEST CASES (Admin API + User API)
=====================================================================
Authentication: POST /api/auth/login {"username":"admin","password":"password"}
  -> 200 {"token": "..."}.  The token is sent as header  Cookie: token=<token>
  to every admin-only call. User calls are sent without any token.

TC-API-01  Create room (Admin API) -> verify in User API
  Steps   : login; POST /api/room; GET /api/room (no token).
  Expected: create returns 2xx; the new room is in the list with the same name, type,
            accessible flag, price, description, image and features.

TC-API-02  Book room (User API) -> verify in Admin API
  Steps   : POST /api/booking (no token); login; GET /api/booking?roomid={id};
            GET /api/report/room/{id}.
  Expected: 201 on booking; admin sees exactly this booking (names, check-in, check-out);
            the report lists the dates as "Unavailable".

TC-API-03  Edit room (Admin API) -> verify in User API
  Steps   : PUT /api/room/{id} (type, price, accessible, description, features changed);
            GET /api/room (no token).
  Expected: 200/202 on update; the user sees all updated values.

TC-API-04  Delete room (Admin API) -> verify in User API
  Steps   : DELETE /api/room/{id}; GET /api/room (no token).
  Expected: 200/202/204 on delete; the room id is absent from the list.

TC-API-05  Create / edit / delete room without authorisation        [Negative]
  Expected: 401 (or 403) for each call; the existing room is unchanged.

TC-API-06  Book room with invalid data                              [Negative]
  Data    : invalid email; firstname "Jo"; empty lastname; phone "123"; no dates.
  Expected: 400 with "errors" (409 when the dates are missing); no booking is stored.

TC-API-07  Home page loads rooms from GET /api/room (cy.intercept)
  Expected: intercepted request returns 200, body.rooms is a non-empty array and
            contains the room created through the Admin API.

TC-API-08  The same dates cannot be booked twice                    [Negative]
  Steps   : book dates; book the same dates again; book overlapping dates.
  Expected: 201, then 409 and 409; the admin still sees exactly one booking.

TC-API-09  Wrong credentials / anonymous access                     [Negative]
  Expected: login with a wrong password -> 401 (or 403);
            GET /api/booking?roomid={id} without token -> 401 (or 403).

=====================================================================
FINDINGS (defects / observations discovered while preparing the tests)
=====================================================================
BUG-01  Reservation page without dates shows an endless spinner.
        Opening /reservation/{id} without ?checkin&checkout never renders the calendar
        (the page waits for a selection that nobody can make). TC-UI-07 documents this.
BUG-02  React hydration error (#418) in the browser console on page load.
        The page still works; the error is ignored by the test support file, all other
        uncaught application errors still fail a test.
BUG-03  Calendar does not show earlier booked dates as "Unavailable".
        GET /api/report/room/{id} returns [{start:"2026-10-20", end:"2026-10-22",
        title:"Unavailable"}] (200), but on /reservation/{id}?checkin=..&checkout=.. the
        calendar (September -> Next -> October) draws only the "Selected" range. The word
        "Unavailable" is not present anywhere in the DOM, no other event / background event
        exists, and reloading the page 3 times gives the same result (not a timing issue).
        Expected: booked days are marked as Unavailable. Automated by TC-UI-08 (the UI part
        is skipped until the bug is fixed).
OBS-01  The home page lists only the first 3 rooms, so tests open a room by its URL.
OBS-02  "Price Summary" counts the selected DAYS as nights (a 3-day drag shows "x 3 nights").
OBS-03  Response codes differ between the public gateway and the room service
        (PUT/DELETE answer 200 on the site, 202 in the service; unauthenticated calls
        answer 401 on the site, 403 in the service), so the API tests accept both.
OBS-05  GET /api/report/room/{id} answers { "report": [ {start, end, title} ] } (an object),
        not a bare array; the tests read both shapes.
OBS-04  Read from the source code, not covered by a test: when the booking API answers 409
        (dates already taken) the gateway returns no "errors" list and the booking form
        reads ".length" of undefined - the page most likely crashes instead of showing a
        message. Covered on API level by TC-API-08.
